# Phase 28: Tour Outreach Mission - Research

**Researched:** 2026-03-12
**Domain:** Email delivery (Resend), HITL approval flow, MissionExecutor step patterns, Gemini draft generation
**Confidence:** HIGH

## Summary

Phase 28 implements TourOutreachMission as a seven-step sequential workflow on top of the MissionExecutor pattern established in Phase 26. The mission fetches PM contact info from existing listing rows (contact_email column added in migration 011), calls Gemini to produce per-listing email drafts, persists those drafts to the mission_drafts table with `draft_type: 'email_draft'` and `user_decision: null`, flips mission status to `waiting_approval`, and then waits. When the student approves in the Concierge UI, two new API routes (`POST /api/missions/[id]/drafts/[draftId]/approve` and `/reject`) handle the decision, trigger Resend delivery for approved drafts, and mark the mission complete once all drafts are resolved.

The DB schema (migration 013) fully covers the phase requirements. No new migration is needed. The mission type to use is `landlord_outreach` — it accurately describes email drafting and outreach, matching the mock data pattern in mock-missions.ts (mission-5). The existing `contact-pm` tool provides the reference pattern for Gemini draft generation but should not be directly invoked by the mission step — the step should reuse its internal helpers (fetchListing, fetchLandlord, generateDraft) by extracting them or writing equivalent inline logic in the mission context.

Phase 28 owns: the TourOutreachMission step runner, the approve/reject API routes, Resend send logic, and the DraftReadyCard UI wiring. Phase 29 owns: replacing mockMissions in ConciergeProvider with real DB data. The DraftReadyCard already exists as a UI component (mock-backed); Phase 28 makes it real by wiring the approve and reject buttons to the new API routes.

**Primary recommendation:** Install the `resend` package, write TourOutreachMission as a self-contained step-array module that uses service-role Supabase for draft writes, use the `landlord_outreach` mission type, and keep Resend behind a thin wrapper so it is mockable in Vitest tests.

### Pattern 1: Step-array Mission Module

**What:** Each mission is a module that exports an array of `MissionStep` objects. The MissionExecutor iterates the array, calling each step's `run` function with a shared `StepContext`.

**When to use:** All missions built on top of Phase 26's MissionExecutor.

### Pattern 2: HITL Pause — Status-gate in Executor

**What:** The executor stops at `notify_student` because the step sets mission status to `waiting_approval`. The executor must check status before continuing to the next step: if status is not `active`, halt and return. The approve/reject routes then call a continuation function directly (not re-run the executor from step 0).

**When to use:** Any mission step that requires human decision before proceeding.

**Key insight:** The MissionExecutor's DB-first state means the executor reads mission status from the DB at each step boundary. Setting status to `waiting_approval` in `notify_student` is the correct signal for the executor to stop. The approve route then independently runs the `send_approved` and `log_sent` steps, or calls a `resumeMission(missionId)` function.

**Two valid continuation approaches:**
1. **Continuation function:** `resumeMission(missionId)` re-starts execution from the first incomplete step (detected by checking existing mission_logs). The executor skips already-completed steps by name. Cleaner reuse of step runner logic.
2. **Direct execution in approve route:** The approve route fetches all approved drafts, sends them, and marks the mission complete inline without calling the executor. Simpler, less infrastructure.

**Recommendation:** Use approach 2 (direct execution in approve route) for Phase 28, since the approve route owns the Resend call. Approach 1 requires the executor to understand step resumption — deferred to a future phase if needed.

### Pattern 3: Resend Thin Wrapper

**What:** Isolate the Resend SDK call behind a single function so Vitest tests can mock it without mocking the entire module system.

```typescript
// Source: resend.com/docs/send-with-nodejs (verified 2026-03-12)
// apps/web/lib/missions/send-email.ts

import { Resend } from 'resend';

const resend = new Resend(process.env.RESEND_API_KEY);

export interface SendEmailParams {
  readonly to: string;
  readonly subject: string;
  readonly text: string;
  readonly from?: string;
}

export interface SendEmailResult {
  readonly id: string | null;
  readonly error: string | null;
}

export async function sendEmail(params: SendEmailParams): Promise<SendEmailResult> {
  const { data, error } = await resend.emails.send({
    from: params.from ?? 'CampusNest Concierge <concierge@campusnest.app>',
    to: params.to,
    subject: params.subject,
    text: params.text,
    idempotencyKey: `draft-${params.to}-${Date.now()}`,
  });

  if (error) {
    return { id: null, error: error.message };
  }

  return { id: data?.id ?? null, error: null };
}
```

### Pattern 5: DraftReadyCard Wiring

**What:** The existing DraftReadyCard component currently calls `showMockToast()` on Approve and Edit clicks. Phase 28 replaces these with real API calls.

**Design decision for Phase 28:** DraftReadyCard receives the real `missionId` and `draftId` as props instead of operating purely on mock `data`. The approve button calls `POST /api/missions/[id]/drafts/[draftId]/approve` and shows a success/error toast via sonner (already installed).

### Anti-Patterns to Avoid

- **Calling contactPm tool handler from within a mission step:** contactPm mixes Gemini generation, DB fetching, and ToolResult formatting for the chat UI. Mission steps need raw data and raw text; use the underlying DB queries directly in the step.
- **Using `listing_id` (single) on missions table for multi-listing missions:** The missions table has `listing_id UUID` as a single nullable FK. TourOutreachMission operates on multiple listings. The listing IDs belong in the mission `goal` field as JSON or in the step's StepContext input — not as multiple rows in missions.
- **Inserting mission_drafts from the client:** The RLS policy on mission_drafts allows INSERT only for service role. The executor (server-side, using service role client) must do all draft inserts.
- **Sending email before draft approval:** Never call Resend before `user_decision = 'approved'`. The HITL gate is the entire safety feature.
- **Re-running the full executor on approval:** The approve route should not restart the executor from step 0. This would re-fetch contacts and re-generate drafts. Only run the send + complete steps on approval.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Email delivery | Custom SMTP integration | Resend SDK | Rate limiting, delivery tracking, domain verification all handled; SDK is 3 lines |
| Email template rendering | Custom HTML template string builder | Plain text (this phase) or React Email | Plain text is sufficient for 120-word tour request emails; React Email if HTML styling is needed |
| Idempotent email sends | Custom deduplication logic | Resend `idempotencyKey` param | Resend deduplicates sends with the same key within 24 hours — use `draft-${draftId}` as key |
| Draft versioning | Custom version counter logic | Supabase trigger already handles it | `set_draft_not_current()` trigger on mission_drafts automatically sets `is_current = false` on previous versions before INSERT |
| Mission status transitions | Custom state machine | Direct UPDATE + DB CHECK constraint | The DB CHECK constraint on missions.status already enforces valid transitions; just UPDATE |

**Key insight:** The mission_drafts table already has versioning, Realtime publication, and RLS baked in. The approve/reject routes are thin: validate auth, update a row, call Resend (approve only), check completion.

## Common Pitfalls

### Pitfall 1: Missing RESEND_API_KEY in env
**What goes wrong:** `sendEmail()` throws or returns error at runtime; mission fails silently if error handling is loose.
**Why it happens:** The `.env.example` does not include `RESEND_API_KEY` — it will need to be added. The key is confirmed available but not documented.
**How to avoid:** Add `RESEND_API_KEY=` to `.env.example` as part of this phase. Validate key presence at startup of the approve route.
**Warning signs:** `Resend API key is missing` error in server logs on first approve.

### Pitfall 2: mission_drafts INSERT from wrong client
**What goes wrong:** `new row violates row-level security policy` error when the executor tries to write drafts.
**Why it happens:** The `save_drafts` step must use the service-role Supabase client (`createSecretClient()`), not the anon client. The RLS INSERT policy on mission_drafts has no user-facing policy — only service role can insert.
**How to avoid:** The MissionExecutor (built in Phase 26) should already use service-role client. Verify the StepContext carries service-role supabase, not anon.
**Warning signs:** 403/RLS error only on draft writes, not on missions status reads.

### Pitfall 3: Resend from-address domain verification
**What goes wrong:** Resend rejects emails sent from unverified domains in production. `onboarding@resend.dev` works only for testing.
**Why it happens:** Resend requires domain verification for production sends.
**How to avoid:** Use `onboarding@resend.dev` as the from-address for Phase 28 development and testing. Document that production deployment requires domain verification. Do not block the phase on this.
**Warning signs:** Resend API returns 403 or domain error on production send.

### Pitfall 4: Next.js 15 route params are now async
**What goes wrong:** `params.id` returns undefined or a Promise object instead of the actual value.
**Why it happens:** Next.js 15 changed dynamic route params to be a Promise — `params` must be awaited: `const { id } = await params`.
**How to avoid:** Use `{ params }: { params: Promise<{ id: string; draftId: string }> }` in the route signature and `await params`.
**Warning signs:** TypeError on `params.id` that was working in older Next.js versions. Existing routes in this codebase (e.g., conversations/[id]) already demonstrate the correct pattern.

### Pitfall 5: Gemini prompt for 120-word emails
**What goes wrong:** Gemini generates emails that are too long, too formal, or too generic across multiple listings.
**Why it happens:** Without clear per-listing variable substitution, Gemini produces generic output.
**How to avoid:** Build the prompt with explicit values per listing: `${studentName}`, `${address}`, `${bedrooms}BR`, `$${rentMonthly}/mo`, `${availability}`. Match the exact prompt from the spec verbatim. Test with a listing that has null bedrooms or null rent to verify graceful fallback.
**Warning signs:** Email body says "the unit" without specifics, or exceeds 200 words.

### Pitfall 6: Multi-listing missions and the single listing_id FK
**What goes wrong:** The missions table has `listing_id UUID` (single FK). TourOutreachMission targets multiple listings.
**Why it happens:** The schema was designed for single-listing missions (tour_booking, lease_review). Outreach missions are inherently multi-listing.
**How to avoid:** Store the array of listing IDs in the mission's `goal` field as a JSON string (e.g., `goal: JSON.stringify({ listingIds: [...] })`). The executor reads this from the mission row. Do not add a new column — the `goal TEXT` field is flexible enough.
**Warning signs:** Planner tries to create a separate mission row per listing, which defeats the purpose.

### Pitfall 7: Race condition on "all drafts resolved" check
**What goes wrong:** Two parallel approve/reject calls both check `all resolved` and both try to set mission to `completed`, causing duplicate status updates or constraint violations.
**Why it happens:** The approve and reject routes both include logic to check if all drafts are resolved.
**How to avoid:** Use a Supabase RPC or a single UPDATE with a subquery that atomically checks and sets. Alternatively, accept idempotent duplicate `completed` status writes — the DB CHECK constraint allows `completed → completed` (same value). The `updated_at` trigger fires on each update but the status value is stable.
**Warning signs:** Supabase logs show multiple completed status writes for the same mission.

### Gemini Draft Generation — Focused prompt
```typescript
// Source: contact-pm.ts pattern (verified in codebase) + spec prompt
import { createGeminiClient } from '@campusnest/ai';  // or relative import

async function generateTourDraft(
  studentName: string,
  address: string,
  bedrooms: number | null,
  rentMonthly: number | null,
  availability: { daysOfWeek: string[]; timeWindows: string[] },
  customNote?: string,
): Promise<string | null> {
  try {
    const ai = createGeminiClient();

    const availabilityStr = [
      availability.daysOfWeek.join('/'),
      availability.timeWindows.join(' or '),
    ].filter(Boolean).join(', ');

    const bedroomStr = bedrooms ? `${bedrooms}BR unit` : 'unit';
    const priceStr = rentMonthly ? ` at $${rentMonthly}/mo` : '';
    const noteStr = customNote ? ` ${customNote}` : '';

    const prompt = `Write a friendly, concise email from ${studentName} to the property manager at ${address}. The student is interested in viewing the ${bedroomStr}${priceStr}. They are available ${availabilityStr}.${noteStr} Keep it under 120 words. Warm but professional. Do not be overly formal.`;

    const response = await ai.models.generateContent({
      model: 'gemini-2.5-flash',
      contents: prompt,
    });

    return response.text ?? null;
  } catch {
    return null;  // graceful degradation — caller handles null
  }
}
```

### Approve route — Draft decision + completion check
```typescript
// Source: existing route patterns in apps/web/app/api/ (verified in codebase)
// apps/web/app/api/missions/[id]/drafts/[draftId]/approve/route.ts

export async function POST(
  req: NextRequest,
  { params }: { params: Promise<{ id: string; draftId: string }> }
) {
  const { id: missionId, draftId } = await params;

  // 1. Auth — getUser from bearer token (pattern from cribai/route.ts)
  // 2. Verify mission ownership
  // 3. Fetch draft payload
  // 4. Send email
  const result = await sendEmail({ to, subject, text });
  if (result.error) {
    return Response.json({ error: result.error }, { status: 500 });
  }

  // 5. Mark approved
  await supabase
    .from('mission_drafts')
    .update({ user_decision: 'approved', decided_at: new Date().toISOString() })
    .eq('id', draftId);

  // 6. Check if all drafts resolved
  const { data: pendingDrafts } = await supabase
    .from('mission_drafts')
    .select('id')
    .eq('mission_id', missionId)
    .is('user_decision', null)
    .eq('is_current', true);

  if (!pendingDrafts || pendingDrafts.length === 0) {
    await supabase
      .from('missions')
      .update({ status: 'completed' })
      .eq('id', missionId);
  }

  return Response.json({ draftId, emailId: result.id });
}
```
